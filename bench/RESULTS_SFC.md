# Wave-14 SFC-Layout Benchmark — A2's space-filling-geometry decision table, priced

**Agent:** Impl-S, Cohort Delta (implementers), Wave 14 · 2026-11-15
**Feature measured:** the SFC layouts (A2 §2.4's decision table, executable): `morton list<int, dims=[n1, n2]>` — tensor iteration with per-element indexed access (one contiguous lane reservation, no directory, addr = base + interleave(i, j)·8; the interleave feature-dispatched once per process per C2.8), and `hilbert map<int, int>` — spatial range queries (the Butz/Skilling key computed once per insert, the sorted lane IS the index, the box query a Tropf–Herzog/Lawder–King segment advance whose per-box key range is computed once and cached, amortized over the yielded entries — A2 §2.4).
**Machine:** Apple M4, macOS 27.2.1 (darwin27, arm64), 16 GB · single-threaded
**Toolchain:** snc 0.2.0 (worktree at HEAD past efed454) · Apple clang `-O2` (the snc default `.ll` link)
**Protocol:** SFC_ROUNDS = 5 (the base; per-row multipliers ×2–×50 as noted) so every timed op phase totals ≥ 100 ms (≥ 100× the .sn ms clock, per the W2F discipline); one warmup at base/10, **median of 5 timed runs**; every row prints a deterministic checksum. Raw runs: `results/sn_sfc_bench.txt` (committed).
**Re-run:** `SFC_ONLY=1 ./run_bench.sh` (env `SFC_ROUNDS`, `RUNS`).

## 1 · The shape, and what is held fixed

- **(a) lex_build vs from_lex** — the same 1,048,576 values (1..N, the checksum inputs): 100 rounds of 1M row-major list pushes (into a per-round-cleared scratch list — the steady-state push regime from_lex's own source sits in) vs 100 rounds of the one **blocked reshuffle** `morton_from_lex` (region-scoped: the lane reclaims each round's 8 MB reservation at the block exit; the row includes the zero fill — the honest one-time cost of deterministic reads on reused lane bytes; the checksum is 3 spot reads per round).
- **(b)+(c) the stencil** — a read-only 5-point stencil over the interior of a 1024×1024 grid of int64 values (**8 MB — past this M4's L2**, so the locality effect is real, not cache-resident), three times: over a **row-major twin** (`list<int>`, lexicographic i-then-j), over the **morton buffer lexicographically** (the same (i, j) double loop, `morton_get`), and over the **morton buffer in curve order** (the code IS the linear index: one loop over k, coords recovered per visit by the deinterleave — the O(1)-carry iteration). 100 sweeps per row; **the three checksums are identical** (the same interior cells summed in three orders — the order-independence witness, self-checked in every run).
- **(d) the box queries** — a fully-populated 512×512 hilbert map (262,144 entries, inserted along the curve); 100 random boxes (sides 8..63 — the off-aligned regime) and 400 dyadic boxes (side 32, 32-aligned — A2's "aligned dyadic boxes = exactly 1 cluster"): the segment advance (`hilbert_box_first`/`next` — the per-box key range computed once, the range scan touching only the in-range entries) vs the **full linear scan** over the same entries for the same 500 boxes. **The checksums must satisfy linear == random + dyadic** (count, sum, xor — the exactness claim, self-checked via the `sfc_box_split` line: 157,118 + 409,600 = 566,718; 21,638,316,786 + 50,541,158,400 = 72,179,475,186; the xors fold — verified identical on all 5 runs).
- **(e) interleave** — 100M rounds of the pure interleave+deinterleave pair (`morton_index` + `morton_x` + `morton_y` in a tight in-language loop): the feature-dispatched arithmetic's price. **`sfc_path=0` on every run: this M4 (AArch64) has no BMI2 — the software shift-or path is what runs here** (C2.8; the BMI2 PDEP/PEXT twin exists behind `#if defined(__x86_64__)` + the runtime dispatch, and the systems suite verifies the knob and the reference).

GC threshold pinned to 2×10⁹ (out of every timed phase). Single-threaded.

## 3 · What the numbers say about the decision table

1. **The layout price is real and small — from_lex ≈ one extra build pass (1.6 vs 1.7 ns/value).** The blocked reshuffle (including the 8 MB zero fill) costs about what ONE row-major build pass costs — here ~1.6 ns/value, i.e. ~15% of one 5-read stencil sweep (~10.3 ns/cell), or **~1.5–3% of a multi-sweep program's runtime — right in ICS'99's 2–5% window** (A2 §3's "explicitly worth paying"). The in-language build pays a call boundary per push; the reshuffle amortizes into one C loop — so the reshuffle is not slower than the build, which is the honest amortization statement, not a magic win.
2. **The stencil is the interesting one, and it lands where A2 §2.1 says it should: row-major wins the flat 5-point stencil.** Lexicographic access on row-major storage: 0.7 ns/read (three contiguous 8 KB rows live in L1 — the textbook row-reuse kernel; Abel–Mark 1990: no curve beats row-major on mean neighbor-gap). The SAME lexicographic loop on morton storage: 2.0 ns/read — the **T5b "wastes the layout" price measured: 2.7×** (the warning's guidance — "use soa for axis-committed access" — is exactly the row-major twin). The curve-ordered sweep on the same buffer lands at 2.5 ns/read **total**, but that total includes the per-visit coordinate recovery (morton_x + morton_y — the C2.9 per-access price, itself priced by the interleave row at ~2 ns/call); subtracting the coordinate cost, the curve-ordered READS run at ≈1.0–1.7 ns/read — **at or below the lexicographic-morton reads, in the row-major streaming direction A2 §2.3/T1 predicts** (in-curve-order iteration is a stride-1 buffer scan), but the flat in-language kernel pays the deinterleave to know its coordinates, so the honest TOTAL for this shape is a wash-to-loss against lexicographic morton. **Chatterjee's morton claim is about recursive kernels with contiguous dyadic operands (ICS'99), not flat stencils with full-row reuse — and the flat-stencil numbers here say so.** The asymptotic T5(b) lex-vs-curve miss gap (Θ(N) vs Θ(N/B)) shows up as the direction (~1.2–2× on reads), not the magnitude, at this 8 MB working set — the M4's last-level cache still absorbs most of the scatter.
3. **The query direction is where hilbert's advantage actually lives (C2.9), and the segment advance wins big: 26× on random boxes, 122× on dyadic boxes.** The random-box row (17.2 µs/box) vs the full linear scan (440 µs/box): the segment advance touches only the entries inside the box's key range. The dyadic row (3.6 µs/box) is the tight-range regime — A2's "aligned dyadic boxes = exactly 1 cluster": the range is one contiguous code run, the scan is the box's own 1,024 entries plus the (once-per-box, cached) boundary encoding. **The exactness holds on every box** (the split identity above, machine-checked across all runs — same result set as the linear scan, any order).
4. **The per-box key range must be computed ONCE and amortized (A2 §2.4's own words) — the benchmark caught the alternative.** The first cut of `hilbert_box_next` re-encoded the box boundary on every advance (2,276 µs per random box — a 5× LOSS to the linear scan); computing the range once per query and caching it for the `box_next` chain turned the row into the 17.2 µs win. The benchmark is what made the design honest.
5. **The interleave itself is cheap: ~6 ns per index+x+y triple (~2 ns per op), software-path.** The shift-or spread is ~10 ops — far below an L2 miss, exactly A2 §2.2's "≪ an L2 miss" claim; C2.8's dispatch makes the BMI2 twin (2 PDEP + or, ~3 cycles on Haswell+) a drop-in on x86-64 hardware, unmeasured here because this machine cannot run it (the forced-bmi2 knob is the honest `[E-SFC-PATH]` refusal — pinned in tests/systems/test_sfc.c).

## 4 · The honest caveats

- **`sfc_path=0` on this machine** — every number above is the software path (AArch64 has no BMI2; C2.8). The BMI2 twin exists, is feature-dispatched, and its equivalence claim is verified on BMI2 hardware by the systems suite's knob pass (and by construction on the interleave grid hash).
- **The stencil rows price the LANGUAGE kernel, not the raw loop** — every read is a runtime call (`morton_get` / list index), ~0.5–1 ns of call overhead per read on all three rows equally; the row-major row's 0.8 ns/read shows the calls are not the bottleneck, but the absolute numbers are in-language numbers, not memcpy-rate numbers.
- **The curve-ordered row conflates the read locality with the coordinate recovery** — an in-language kernel needs its (x, y) per visit to address the neighbors, and the deinterleave is the C2.9 per-access price. A `morton` neighbor-code intrinsic (O(1) key-adjacency arithmetic, no deinterleave) is the natural slice-2 addition that would isolate the pure T1 streaming claim.
- **The random-box regime is the slice-1 range scan, not the full Lawder–King jump** — the advance scans every entry inside the box's key RANGE (skipping out-of-box points), which for off-aligned boxes spans a wider code swath than the box itself (A2's honest thin-box degradation, T2(v)). The Lawder–King "next in-box key ≥ c" descent (Θ(k) per jump, the hix algorithm) is the documented slice-2 refinement; with it the random-box row would approach the dyadic row's cost.
- **The timer row is the clock-pair measurement itself** (inherently sub-ms; its checksum sums wall-clock readings and varies by construction — the wave-bench precedent). Every op phase is ≥ 100 ms and every op checksum is bit-identical across runs.
- **Single hilbert map, single morton buffer, no eviction pressure between rows** — the map (4×262,144×8 B ≈ 8 MB of lane) and the morton (8 MB) stay resident across rows; the box rows compare query algorithms on the SAME resident data, which is the comparison's point.
